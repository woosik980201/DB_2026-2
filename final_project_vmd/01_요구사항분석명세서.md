## 1. 배경과 목적

패션 편집샵에서는 마네킹에 착장한 상품이 마지막 재고(Last Piece)여서 판매를 위해 회수하고 다른 상품으로 교체하는 일이 발생한다. 이때 대체 상품이 같은 마네킹에 이전에 사용되었는지 확인하기 어렵다. 본사 VMD 담당자와 매장 직원이 시즌별 디스플레이 계획, 상품 배치, VMD 작업, 점검 결과를 일관되게 관리하도록 관계형 데이터베이스를 설계한다.

핵심 원칙: 기존 상품 배치의 상품·집기·디스플레이·시작일을 덮어쓰거나 기록을 삭제하지 않는다. 종료 정보를 기록한 뒤, 후속 배치가 필요한 경우 새 배치 기록을 추가한다.

## 2. 사용자와 범위

- 본사 VMD 담당자: 시즌·디스플레이 계획, 작업 배정, 진행 현황·점검 조회
- 매장 직원: 배치·착장 이력 조회, VMD 작업 및 완료 기록
- 포함: 매장, 구역(VP/PP/IP), 집기(마네킹·행거·선반), 시즌/캠페인, 스타일, SKU 상품, 디스플레이, 상품 배치·이력, 직원, VMD 작업·배정, 점검, 조회
- 제외: 판매·결제, 실시간 재고 수량, 발주·물류, 고객 정보, 이미지 파일 저장, AI 이미지 생성, 웹·모바일 UI, 실제 인증
- Last Piece는 종료 사유로 기록하지만 재고 수량은 관리하지 않는다. SKU는 착장 이력을 식별하는 단위이며 재고 관리를 뜻하지 않는다.

### 5.5 긴급 회수 사후 등록 절차

1. 직원이 상품을 회수하고 실제 회수 시각을 메모한다.
2. `VMD_TASK`를 등록한다. 예정일은 NULL일 수 있고, 등록일시는 시스템 입력 시각이다.
3. 작업을 처리한 뒤 완료일을 기록한다.
4. 같은 트랜잭션에서 `PLACEMENT`의 종료일(실제 회수 시각), 종료작업ID, 종료 사유를 기록한다.
5. 대체 상품은 실제로 착장할 때 신규 배치로 등록한다.

**한계:** 사후 등록 전에는 실제 매장 상태와 DB 조회 결과가 일치하지 않을 수 있다. 회수된 상품이 현재 착장으로 조회될 수 있으며, 이 차이는 사후 등록 후 해소된다.

### STYLE 분리 근거

브랜드, 상품명, 카테고리가 색상·사이즈와 관계없이 스타일별로 동일하다는 업무 전제에서 다음 함수 종속성이 성립한다.

```text
상품ID -> 상품코드, 스타일코드, 색상, 사이즈
스타일코드 -> 브랜드, 상품명, 카테고리
(스타일코드, 색상, 사이즈) -> 상품ID
```

한 테이블에 함께 두면 `상품ID -> 스타일코드 -> 브랜드, 상품명, 카테고리`의 이행적 함수 종속이 생겨 3NF를 만족하지 못한다. `STYLE`을 분리하면 SKU마다 공통 정보를 반복 저장하지 않고 수정 이상을 줄일 수 있다.

## 7. 무결성 구현 수단

아래 표는 구현 계획이며, SQL 구현과 테스트는 아직 수행하지 않았다.

| 구분 | 잘못된 입력 차단 | 대상 규칙 | 상태 |
|---|---|---|---|
| 기본 제약 | 가능 | PK, 단일 FK, `NOT NULL`(BR-10, BR-29), `UNIQUE`(작업·직원 중복 배정, 상품코드, 스타일코드+색상+사이즈) | 계획 |
| `CHECK` | 가능, 같은 행 안에서만 | BR-11, BR-18, BR-20, BR-21, BR-24, BR-39, 착장부위 값 목록 | 계획 |
| 복합 FK | 가능 | BR-22, 수업 범위에서 구현 가능할 때만 | 검토 중 |
| 사후 검증 SQL | 불가, 위반 데이터 검출 | BR-19, BR-22 대체안, BR-23, BR-30 필수 여부, BR-32, BR-34, BR-35 | 계획 |
| 운영 절차 + 테스트 | 불가, 절차로 관리 | BR-12, BR-26, 모든 최초 배치의 작업 등록 전제 | 계획 |

복합 FK를 쓰면 `PLACEMENT`의 작업ID와 디스플레이ID 조합을 `VMD_TASK`에 대응시킨다. 추가 컬럼은 필요 없고, 종료작업ID가 NULL인 현재 배치는 FK 검사 대상에서 제외된다.
